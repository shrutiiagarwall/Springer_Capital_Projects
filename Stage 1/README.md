**Jira:** DHAP-34 | **Owner:** shruti | **Status:** ready for local run

This project ingests the **MailEx** (Email-Event-Extraction) dataset into a
PostgreSQL data warehouse using Apache Airflow, running entirely inside Docker.
A teammate with no prior knowledge of MailEx can follow this runbook end-to-end.

## 1. What is MailEx and why did it need flattening?

**MailEx** (Srivastava et al., EMNLP 2023) is the first dataset for email event
extraction.  It consists of **1 500 email threads** (~4 K emails) drawn from the
Enron corpus and annotated with ~9 K event instances across 10 event types
(e.g. `Request_Meeting`, `Deliver_Data`) and 76 argument roles.

### Raw format

Each email thread is a single **JSON file**.  The schema is deeply nested:

```
{
  "events": {
    "turn_0": {
      "Request_Action": {
        "labels":   [ ["B-Action Members", "I-...", "O"] ],  // BIO per token
        "triggers": [ "{'words': 'we need', 'indices': '0 1'}" ],
        "extras":   [ "Query Items : Action Value" ]
      }
    },
    "turn_1": { ... }
  },
  "sentences": [
    ["we", "need", "a", "fourth", "again"],  // turn_0 tokens
    ["what", "about", "hull", "?"]            // turn_1 tokens
  ]
}
```

This structure cannot be loaded directly by a SQL ingestion tool — it requires
traversal of four nesting levels (file → turn → event_type → trigger list).

### Flattening step

`scripts/flatten_to_csv.py` walks every JSON file in `data/train`, `data/dev`,
and `data/test`, and emits **one CSV row per (thread, turn, event_type, trigger)**
combination.  The output is `data/raw/email_event_extraction.csv` — a flat,
tidy table that the Airflow DAG treats as if it were a spreadsheet downloaded
from SharePoint.

The DAG **never reads JSON directly**.  Its job starts at the CSV.

## 3. Dataset status

`email_event_extraction/manifest.yaml` records two status fields that track the
dataset's analysis lifecycle:

| Field | Value | Meaning |
|---|---|---|
| `status` | `"."` | Blank / not yet formally recorded (code 103) |
| `status2` | `pending` | Dataset analysis is still in progress |

The DAG's `read_csv` task reads these fields at run-time and logs them.
**If `status2` is `"pending"`**, the task emits a `WARNING` in the Airflow logs:

```
WARNING — DATASET STATUS WARNING: manifest.yaml reports status2='pending'.
Dataset analysis for 'email_event_extraction' is still in progress.
The pipeline will continue, but analytical results should be treated as
preliminary until the status is updated.
```

The pipeline **does not stop** on a pending status — the warning is informational
only.  When analysis is complete, update `manifest.yaml` by setting
`status2: complete` (or removing the field) to suppress the warning on future runs.

## 4. Prerequisites

| Requirement | Version |
|---|---|
| Docker Desktop (Windows/macOS) or Docker Engine (Linux) | ≥ 24 |
| Docker Compose plugin | ≥ 2.20 |
| Python (host machine, for flatten script only) | ≥ 3.9 |
| Free ports | 8080 (Airflow UI), 5433 (postgres-target) |

**Nothing else is required.**  Airflow, pandas, psycopg2, and all other
dependencies run inside Docker containers.

> **Windows note:** If you see permission errors on the `airflow_logs` volume,
> set `AIRFLOW_UID=0` in your `.env` to run as root inside the container (fine
> for a local dev environment).

## 5. Step 0 — Run the flatten script (one time)

This is a one-time pre-processing step.  Run it on your **host machine** (not
inside Docker) before starting the stack.

```bash
# From the project root (stage-1-csv-to-postgres/):
python scripts/flatten_to_csv.py
```

Expected output:
```
Output => .../stage-1-csv-to-postgres/data/raw/email_event_extraction.csv
Data root => .../data/data

Processing split='train': 1200 files ...
  => 7207 rows written for split='train'
Processing split='dev': 150 files ...
  => 1016 rows written for split='dev'
Processing split='test': 150 files ...
  => 945 rows written for split='test'

Done. Total rows: 9168
CSV saved to: .../data/raw/email_event_extraction.csv

Bad CSV (for failure-test) written to: .../data/raw/email_event_extraction_bad.csv
  Missing column: event_type
  Bad dtype:      num_arguments = 'NOT_AN_INTEGER' (expected integer)
```

The script is idempotent — re-running it overwrites the CSV files.

## 6. Step 1 — Start the stack

```bash
# From the project root (where docker-compose.yaml lives):
docker compose up -d
```

This starts five containers:

| Container | Role |
|---|---|
| `mailex_postgres_meta` | Airflow metadata database (internal) |
| `mailex_postgres_target` | Data warehouse (your email_events table) |
| `mailex_airflow_init` | One-shot init: DB migrate, admin user, Connection, DDL |
| `mailex_airflow_webserver` | Airflow UI → http://localhost:8080 |
| `mailex_airflow_scheduler` | Task scheduling (LocalExecutor) |

Wait ~60 seconds for init to complete, then open **http://localhost:8080**.

**Credentials:** `admin` / `admin`

### Check that everything is healthy

```bash
docker compose ps
```

All services except `airflow-init` should show `running (healthy)`.
`airflow-init` will show `exited (0)` — that is correct.

## 7. Step 2 — Trigger the DAG

### Via the Airflow UI

1. Open http://localhost:8080 and log in as `admin` / `admin`.
2. Find the DAG **`load_email_event_extraction_to_postgres`**.
3. Toggle it **ON** (the toggle on the left).
4. Click the **▶ Trigger DAG** button (the play icon on the right).
5. Watch the graph view: tasks turn green as they succeed.

### Via the CLI

```bash
docker compose exec airflow-scheduler \
    airflow dags trigger load_email_event_extraction_to_postgres
```

Check status:
```bash
docker compose exec airflow-scheduler \
    airflow dags list-runs --dag-id load_email_event_extraction_to_postgres
```

Watch task logs in real time:
```bash
docker compose exec airflow-scheduler \
    airflow tasks logs load_email_event_extraction_to_postgres load_to_postgres <run_id>
```

## 9. Re-running is safe (no duplication)

The `load_to_postgres` task uses **TRUNCATE then INSERT**:

```
TRUNCATE TABLE email_events RESTART IDENTITY;
INSERT INTO email_events (...) VALUES ...
```

Re-triggering the DAG any number of times always produces exactly one clean
copy of the data.  The TRUNCATE and all INSERTs run inside a **single
transaction**: if any INSERT fails, the TRUNCATE is rolled back and the table
retains its previous contents.

## 10. Failure test — validate_schema rejects the bad CSV

The flatten script also produced `data/raw/email_event_extraction_bad.csv`,
which is deliberately malformed:

- Missing column: **`event_type`** (required, NOT NULL)
- Wrong dtype: **`num_arguments = 'NOT_AN_INTEGER'`** (must be integer)

### How to run the failure test

Swap the bad CSV in place of the good one, trigger the DAG, then restore.

**PowerShell (Windows):**

```powershell
# 1. Back up the good CSV and swap in the bad one
Copy-Item data\raw\email_event_extraction.csv data\raw\email_event_extraction_good.csv
Copy-Item data\raw\email_event_extraction_bad.csv data\raw\email_event_extraction.csv -Force

# 2. Trigger the DAG (expect validate_schema to fail)
docker compose exec airflow-scheduler `
    airflow dags trigger load_email_event_extraction_to_postgres

# 3. Restore the good CSV
Copy-Item data\raw\email_event_extraction_good.csv data\raw\email_event_extraction.csv -Force

# 4. Trigger again to confirm success
docker compose exec airflow-scheduler `
    airflow dags trigger load_email_event_extraction_to_postgres
```

**bash (macOS/Linux):**

```bash
# 1. Back up the good CSV and swap in the bad one
cp data/raw/email_event_extraction.csv data/raw/email_event_extraction_good.csv
cp data/raw/email_event_extraction_bad.csv data/raw/email_event_extraction.csv

# 2. Trigger the DAG (expect validate_schema to fail)
docker compose exec airflow-scheduler \
    airflow dags trigger load_email_event_extraction_to_postgres

# 3. Restore the good CSV
cp data/raw/email_event_extraction_good.csv data/raw/email_event_extraction.csv

# 4. Trigger again to confirm success
docker compose exec airflow-scheduler \
    airflow dags trigger load_email_event_extraction_to_postgres
```

### Expected failure

The `validate_schema` task raises:

```
ValueError: Schema validation FAILED with 2 error(s):
  • MISSING COLUMN: 'event_type' not found in CSV.
  • TYPE VIOLATION: Column 'num_arguments' must be integer but contains
    non-integer values: ['NOT_AN_INTEGER']. (Original error: ...)

Fix the upstream CSV or schema.yaml and re-run the DAG.
```

The task turns **red** in the Airflow UI.  The `transform` and `load_to_postgres`
tasks never run, so no bad data reaches Postgres.

## 11. Architecture diagram

```
Host machine
│
├── scripts/flatten_to_csv.py  ──► data/raw/email_event_extraction.csv
│       (run once, Python on host)
│
└── docker compose up
        │
        ├── [postgres-meta]   <- Airflow internal state (DO NOT query)
        │
        ├── [postgres-target] <- mailex_warehouse
        │       email_events table (port 5433 on host)
        │
        ├── [airflow-init]  (runs once)
        │       1. airflow db migrate
        │       2. create admin user
        │       3. create postgres_target Connection
        │       4. run email_event_extraction/ddl.sql -> CREATE TABLE email_events
        │
        ├── [airflow-webserver]  http://localhost:8080
        │
        └── [airflow-scheduler]
                │
                └── DAG: load_email_event_extraction_to_postgres
                        │
                        ├── read_csv          (load CSV; log manifest status)
                        ├── validate_schema   (check columns & dtypes)
                        ├── transform         (clean, dedup, NULL-normalise)
                        └── load_to_postgres  (TRUNCATE + INSERT)
```

## 12. Common troubleshooting

### Port 8080 already in use

```bash
# Find the PID using port 8080
netstat -ano | findstr :8080      # Windows
lsof -i :8080                     # macOS/Linux

# Change the host port in docker-compose.yaml:
#   ports:
#     - "8081:8080"
# Then: docker compose up -d
```

### Port 5433 already in use

Same approach — change the host port for `postgres-target` in
`docker-compose.yaml` (the container-side port stays 5432).

### Volume permission errors (Linux)

```bash
# Set AIRFLOW_UID to your host user's UID:
echo "AIRFLOW_UID=$(id -u)" >> .env
docker compose down -v
docker compose up -d
```

### "Connection postgres_target not found" in the DAG

```bash
# Check that airflow-init completed successfully:
docker compose logs airflow-init | grep -E "(Connection|error|Error)"

# Manually re-create the connection:
docker compose exec airflow-webserver \
    airflow connections add postgres_target \
    --conn-type postgres \
    --conn-host postgres-target \
    --conn-login airflow \
    --conn-password airflow_dev_password \
    --conn-schema mailex_warehouse \
    --conn-port 5432
```

### DAG not visible in the UI

```bash
# Check for Python syntax errors in the DAG file:
docker compose exec airflow-scheduler \
    python /opt/airflow/dags/load_email_event_extraction_to_postgres.py

# Check scheduler logs:
docker compose logs airflow-scheduler | tail -50
```

### airflow-init fails: "psql: command not found"

The `apache/airflow:2.9.3` image does not include `psql` by default.  If you
see this error, run DDL manually after init:

```bash
docker compose exec postgres-target \
    psql -U airflow -d mailex_warehouse -f /dev/stdin < email_event_extraction/ddl.sql
```

Or copy the file into the target container:

```bash
docker compose cp email_event_extraction/ddl.sql postgres-target:/tmp/ddl.sql
docker compose exec postgres-target \
    psql -U airflow -d mailex_warehouse -f /tmp/ddl.sql
```

> **Permanent fix:** Use a custom Airflow image that installs `postgresql-client`.
> A `Dockerfile` can be added as a follow-up (out of scope for DHAP-34).

### Reset everything and start fresh

```bash
docker compose down -v   # stops containers AND deletes volumes (all DB data)
docker compose up -d
```
